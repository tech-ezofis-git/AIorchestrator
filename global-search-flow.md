# EZOFIS AI Orchestrator — Global Search Flow

**Question this feature answers:** "Where does this term exist in this tenant?"

**Key design point for the walkthrough:** `global_search` is a **deterministic, code-driven pipeline**, not an LLM tool-calling agent. The chat LLM never decides *which* search to run and never invents hits — it only (optionally) paraphrases hits it's handed. That's why `usage` comes back `null`: no completion tokens are spent choosing tools or generating findings.

```mermaid
flowchart TD
    A["Client / Console<br/>POST /chat<br/>intent: global_search<br/>tenantId, query, specificId?"] --> B{"Orchestrator<br/>Intent Router"}

    B -->|"intent == global_search"| C["Deterministic Global Search Pipeline<br/>(no LLM tool selection)"]
    B -->|"other intents"| Z["LLM Agent / Tool-Calling Path<br/>(not used for global_search)"]

    C --> D{"Validate request<br/>tenantId + query required"}
    D -->|"missing"| E["400 — reply with error,<br/>global_search_result: null"]\
    D -->|"valid"| F{"specificId<br/>present?"}

    F -->|"yes"| G["Scope = single repository<br/>(UUID lock)"]
    F -->|"no"| H["Scope = all repositories<br/>in tenantId"]

    G --> I["Search Fan-out<br/>(runs both paths, same scope)"]
    H --> I

    I --> J["SQL Search<br/>exact / pattern match on<br/>structured fields: doc numbers,<br/>PO/invoice IDs, indexed metadata"]
    I --> K["Embedding / Vector Search<br/>semantic similarity over<br/>indexed content chunks"]

    J --> L["Merge + Dedupe<br/>→ flat list of typed hits<br/>(repo, doc id, field, snippet, score, matchType)"]
    K --> L

    L --> M["Rank hits<br/>exact SQL match > partial match ><br/>semantic similarity score"]

    M --> N["Assemble global_search_result JSON<br/>{ query, hits[] }"]

    N --> O["Compose reply text<br/>templated from hits only —<br/>no free-generation, no invented hits"]

    O --> P["Response<br/>{ reply, usage: null, global_search_result }"]

    P --> A
```

## Stage-by-stage captions

| Stage | What happens | Why it matters |
|---|---|---|
| **Intent Router** | Reads `intent: "global_search"` and routes straight into the fixed pipeline instead of the LLM agent/tool-calling path used for other intents. | This is the guardrail: the LLM is architecturally never given a chance to "pick" global search as a tool or skip it — the router decides before any model is invoked. |
| **Validate request** | Checks `tenantId` and `query` are present. `specificId` is optional. | Fails fast with a normal error response if required fields are missing — no partial/guessed search. |
| **Scope resolution** | `specificId` present → lock to that one repository UUID. Otherwise → search every repository the tenant has. | Keeps the search boundary explicit and tenant-isolated; no cross-tenant leakage possible since scope is derived only from validated input. |
| **SQL Search** | Exact/pattern matching against structured, indexed fields — document numbers, PO/invoice IDs, other typed metadata columns. | This is what makes a query like `PO-60001` resolve precisely — a lexical/structured match, not a "guess" by the model. |
| **Embedding / Vector Search** | Similarity search over vectorized content chunks for the same query, same scope. | Catches semantic/free-text matches SQL can't — e.g. the term appears in a document body but not as an indexed field. |
| **Merge + Dedupe** | Combines both result sets into one flat, typed hit list, removing duplicates where SQL and embedding hits point to the same object. | Produces a single, consistent list rather than two disjoint result sets the client would have to reconcile. |
| **Rank hits** | Orders hits — exact SQL matches first, then partial matches, then embedding similarity score. | Deterministic ranking rule, not model judgment — reproducible given the same data. |
| **Assemble `global_search_result`** | Packages `{ query, hits[] }` exactly as returned to the client. | This is the ground truth object; nothing downstream can add to or alter these hits. |
| **Compose reply text** | A short natural-language summary is templated directly from the hit list (e.g. counts, repositories, top matches) — not freely generated by an LLM. | Guarantees the human-readable `reply` can never say something the `hits[]` array doesn't support. This is also why `usage` is `null`: no model completion is billed for this step. |
| **Response** | Returns `reply`, `usage: null`, and `global_search_result` to the caller. | Client gets both a quick-read summary and the full structured hit list to render/filter itself. |

## The one rule to underline in the walkthrough
> For `intent: "global_search"`, the LLM is not in the decision loop. It doesn't choose SQL vs. embeddings, doesn't decide scope, and doesn't author hits. Those are all fixed, deterministic pipeline steps. The only thing that could resemble "generation" is a templated summary sentence built strictly from the `hits[]` the pipeline already produced.
